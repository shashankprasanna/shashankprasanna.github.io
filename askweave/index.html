AskWeave: An agentic docs assistant for macOS - traced, monitored, and evaluated with W&B Weave.

Building a native macOS agentic documentation assistant and instrumenting it end to end with W&B Weave — tracing, online monitoring, and evaluation

A native macOS Swift app

There are roughly 60 million registered Apple developers and 2.5 billion active Apple devices. By recent estimates about 63% of those developers are shipping AI features in their apps, on-device with Core ML and MLX or through cloud APIs.

W&B Weave is an observability platform for LLM applications, but only ships SDKs for Python and TypeScript.

So if you are building an AI app for Apple platforms and you want it traced, the supported path is to emit OpenTelemetry directly.

What I built: AskWeave, an agentic assistant that answers questions about the Weave documentation. It is a native macOS app on Apple’s Foundation Models framework. It decides for itself when to search, read, run code or answer, and everything it does is traced, monitored and evaluated in Weave.

Here’s what we’ll cover:

  1. What AskWeave does and how to run it
  2. Data prep — turning 67 doc pages into a hybrid search index
  3. Model prep — four LLM backends behind one interface
  4. The agent loop — three phases, and the four invariants that were each a bug first
  5. Running code to verify code — a sandboxed Python tool
  6. Tracing — Weave’s agent data model over raw OpenTelemetry
  7. Signals — online monitoring, and what it caught that error rates couldn’t
  8. Evaluation — a dataset designed to fail, and what happened when I acted on the results
  9. When your instruments disagree

This is a build log rather than a tutorial: the decisions, the trade-offs, and the things that broke.

Why a Mac-native app

The best Mac apps are native Mac apps. Foundation Models gives you an on-device language model with no API key, no network and no per-token cost. MLX lets you run a larger open-weights model in-process on the GPU. And Foundation Models framework lets you build agentic experiences across on-device and hosted models like Claude and Gemini through one consistent interface, so the same agent code runs against a 4B model on your laptop and a frontier model in the cloud.

What AskWeave does

  • Answers questions about the Weave documentation using an agentic tool-calling loop — it decides at each step whether to search, read a page, run code, or answer
  • Verifies its own answers against the source before responding
  • Runs code it is about to show you, in a sandbox, to check the snippet works
  • Multi-turn conversations, with context management on a 4096-token budget
  • Runs on four LLM backends — Apple on-device, MLX in-process, Claude, or any OpenAI-compatible server
  • Shows the agent loop live while it is working, so the decision-making is visible rather than assumed
  • Emits Weave’s agent tracing data model as raw OpenTelemetry, from Swift
  • Persists conversations with SwiftData, generates conversation titles, streams responses, and can be stopped mid-turn
The agent deciding what to do next, live.

Running it

# 1. Credentials — the app reads ~/.netrc for its Weave telemetry key
pip install weave && weave login

# 2. Build
cd AskWeave && xcodebuild -project AskWeave.xcodeproj -scheme AskWeave -configuration Debug build

# 3. Optional: the local MLX model (2.9 GB, not bundled)
hf download mlx-community/Qwen3.5-4B-MLX-4bit \
  --local-dir AskWeave/AskWeave/Resources/Qwen3.5-4B-MLX-4bit

Then ⌘, to pick a backend. Skip step 3 and use Apple’s on-device model instead: it is free, private, and the more constrained configuration.

Requires macOS 27 and Xcode 27. Open the project in Xcode once and approve the macro trust prompt. Swift macros need per-fingerprint approval, and changing a package pin revokes it.

Architecture, code-free

Before any implementation detail, here’s the whole system.

flowchart LR
    Q(["Your question"]) --> LOOP

    subgraph app["AskWeave.app — Swift, on your Mac"]
        LOOP["Agent loop<br/>research → verify → answer"]
        TOOLS["Tools<br/>search_docs · read_page<br/>check_claim · run_snippet"]
        IDX[("Hybrid index<br/>1081 chunks, bundled")]
        MODEL["Language model<br/>on-device · MLX · Claude<br/>· OpenAI-compatible"]

        LOOP <-->|"tool call / result"| TOOLS
        TOOLS <--> IDX
        LOOP <-->|"prompt / completion"| MODEL
    end

    LOOP --> A(["Answer with citations"])
    LOOP -. "spans, OTLP protobuf" .-> W[("W&B Weave")]

The loop cycles between the model and the tools until it has enough to answer. Two things about that picture shaped everything downstream:

  1. The index ships inside the app. No vector database, no network call for retrieval. 1081 chunks and their embeddings live in the app bundle.
  2. The dotted arrow is hand-built protobuf. There is no Weave SDK anywhere in this diagram.

Weave’s Signals score those turns after they arrive, and the evaluation harness drives the same loop from Python over localhost. Both come later in the post.

Data prep: hybrid search index

An agent is only as good as what it can find. This part is plain ML engineering in Python, in two notebooks.

Fetching the corpus

Weave’s docs are served as markdown if you ask nicely — every page has a .md endpoint. I pulled 67 pages across the tracking, evaluation, core-types, tools and platform guides, plus the Python SDK reference, and pinned them with a manifest:

{
  "source": "https://docs.wandb.ai",
  "fetched_at": "2026-08-07",
  "page_count": 67,
  "license": "Apache-2.0 (wandb/docs)"
}

Chunking

Documentation has structure, so the chunker uses it: split on H2 headings first, fall back to paragraphs, then lines. MDX tab blocks get split apart — a page showing the same operation in Python and TypeScript should produce two chunks, not one confusing one.

Target 350 tokens, hard cap 480, discard anything under 40. That produced 1081 chunks from 67 pages.

Each chunk carries its heading path, so the embedded text has context a bare paragraph wouldn’t:

Trace agents > Instrument an agent > Python

Use weave.start_turn to open a turn...

Embeddings and the search index

BAAI/bge-small-en-v1.5, fp16, 384 dimensions — small enough to bundle at 66 MB, good enough for this corpus. The same weights ship inside the app, so the query encoder and the index encoder are provably identical.

Retrieval is hybrid:

flowchart LR
    Q["query"] --> BM25["BM25<br/>IDF + Porter stemmer<br/>identifier decomposition"]
    Q --> DENSE["Dense<br/>bge-small cosine"]
    BM25 --> RRF["Reciprocal Rank Fusion<br/>k=60"]
    DENSE --> RRF
    RRF --> CAP["max 2 chunks per page"]
    CAP --> OUT["results"]

Why both. BM25 nails exact identifiers — weave.init, WEAVE_DISABLED, redact_pii_fields. Dense retrieval nails paraphrase — “how do I stop it logging personal info”. Documentation questions are constantly one or the other, and often both in the same sentence.

The identifier decomposition is a small thing that matters a lot: tracing_sample_rate also indexes as tracing, sample, rate. Without it, a user who types “sampling rate” misses the page that answers them.

The 2-chunks-per-page cap stops one verbose page from filling the entire result set. On a 4096-token context window, that’s not a nicety.

Honest caveat: the first version behind this interface was six pages scored by term frequency with no IDF and no stemming, and it demonstrably returned the wrong pages. It sat behind a DocsIndex protocol, which meant replacing it touched nothing above. The seam was worth more than the first implementation.

Model prep: four backends, one interface

Foundation Models framework is designed as one consistent interface over multiple model providers. That’s a strong claim, and I wanted to test it rather than assume it. So AskWeave runs on four backends:

BackendModelContextNotes
Apple on-devicesystem model4,096Free, private, runs on the ANE. The hard mode.
MLX in-processQwen3.5-4B-4bit32,7682.9 GB bundled, GPU, no network
Claudeclaude-haiku-4-5200,000Key in the login keychain
OpenAI-compatibleanythingconfigurableLM Studio, llama.cpp, vLLM

Switching is a property change, not a refactor. Everything that scales with the context window — phase budgets, retrieval payload size, history transform — derives from contextSize:

var searchChunks: Int {
    tuning.searchChunks > 0 ? tuning.searchChunks : (contextSize >= 16_000 ? 4 : 2)
}

That line is the fix for a bug I’ll admit to: I originally hard-coded a 4-chunk retrieval payload, ran it on the 4096-token on-device model, and watched the model degenerate into repeating itself. I spent a while blaming the small model. It was a configuration bug. The context was overflowing and the model was doing its best.

What differs between backends

One interface, but not one behaviour. The differences are worth knowing before you rely on any of them:

What I assumedWhat actually happens
.toolCallingMode(.required) forces a tool callEnforced on-device. Advisory over chat-completions — the backend can just ignore tool_choice
.toolCallingMode(.disallowed) prevents tool callsAlso advisory. I watched a model emit <tool_call><function=search_docs> as its user-facing answer
Tools run one at a timeThree backends do. Claude returns several tool_use blocks per message and the framework runs them concurrently
reasoningLevel is availablePrivate Cloud Compute and third-party only. Not on-device.
GenerationOptions has a repetition penaltyIt does not. Temperature, top-p, top-k only.

The concurrency one caused an actual crash — EXC_BAD_ACCESS — because my session-property writes weren’t holding a lock. Three backends had never exercised that path in parallel, so the bug simply didn’t exist until Claude showed up.

A pattern I kept running into: a property observed on one backend gets written down as a property of the framework. It usually is not. Building the control group is cheap, and in this project it changed the conclusion nearly every time.

The agent loop: a baton pass, not a while loop

The traditional way to build an agent loop is while — call the model, check if it wants a tool, run the tool, loop. That’s easy to explain line by line, and it throws away the framework’s entire reason for existing, and it makes multi-turn history management your problem.

Foundation Models framework lets you define agentic loops declaratively vs. traditional imperative hand rolled loops. It describes two patterns for multi-step agents. In a baton pass, several profiles share one transcript and hand control between themselves — the agent moves through stages, and each stage sees everything the previous ones did. In phone-a-friend, a tool spawns a separate short-lived session with its own isolated transcript, which answers a question and disappears. One continuous conversation that changes gear, versus delegating to a specialist who never sees the rest.

AskWeave is a baton pass: several profiles, a variable choosing which is active, a tool letting the model set that variable, and one shared transcript. A DynamicProfile’s body re-evaluates before every model request, so a single session.respond(to:) call flows through all of your phases.

AskWeave has three:

stateDiagram-v2
    [*] --> Research
    Research --> Verify: finish_research
    Verify --> Answer: finish_verification
    Answer --> [*]

    note right of Research
        search_docs
        read_page (withdrawn after 3)
        finish_research
    end note

    note right of Verify
        check_claim
        run_snippet
        finish_verification
    end note

    note right of Answer
        no tools
        toolCallingMode(.disallowed)
    end note

Research gathers evidence. Verify checks each claim against its source. Answer writes the response — with no tools at all, so the only legal move left is to reply. That’s the loop’s exit condition, expressed structurally rather than as a counter.

The phase itself is derived from session state, so the profile just asks:

var body: some DynamicProfile {
    if !researchComplete {
        PhaseProfile { BaseInstructions(); ResearchToolset(...) }
    } else if !verifyComplete {
        PhaseProfile { BaseInstructions(); VerifyToolset(...) }
    } else {
        PhaseProfile { BaseInstructions(); AnswerDirective() }
            .toolCallingMode(.disallowed)
    }
}

Four invariants, each of which was a bug first

1. The model ends each phase, not a counter. My first version flipped a didSearch flag on the first search_docs call — which made “research” exactly one query, while the instructions cheerfully told the model to search repeatedly. Instruments showed the consequence plainly: the second inference was labelled VERIFY while still calling read_page. Structure and prompt disagreed, and the model routed around it.

Now the model calls finish_research when it’s done. A step counter would be deterministic and would take the control-flow decision away from the model — which is precisely the behaviour I wanted to observe.

2. Grounding lives in the tool, not the phase machine. If the model can end research whenever it likes, what stops it ending immediately and answering from memory? finish_research refuses while nothing has been retrieved:

guard !retrievedPageIDs.isEmpty else {
    return "You haven't retrieved anything yet. Search the docs first."
}

The guarantee lives in the one place the model can’t route around.

3. The tool set shrinks as evidence accumulates. read_page is withdrawn after three full reads. Left available, a stuck model will re-read the same four pages forever — I watched a 17-inference loop do exactly that. Taking the option away forces the finish_research decision.

But withdrawing a tool outright kills the turn, which I also learned the hard way. Withdrawn tools stay registered as stubs that redirect.

4. Per-turn state resets at the end of the turn. The obvious place to reset per-turn state is onPrompt — start of turn, clear the flags. Turn 1 was perfect. Turn 2 answered “the documentation doesn’t state this” without retrieving anything.

The framework resolves which profile is active before running that profile’s onPrompt. So by the time my reset ran, the turn had already been planned as an answer-phase turn with tools disabled. The reset was arriving one request too late.

It now runs on the answer phase’s onResponse — the trailing edge of the previous turn.

Which of these did the tracing catch?

Worth being specific, since instrumenting early is easy to recommend and harder to justify.

Invariants 3 and 4 were found in Weave, and I am not sure how else I would have found them. The turn-2 bug produces a turn that looks entirely normal from the outside: a confident answer, no error, no warning. In the Agents view it is unmistakable — the turn has a chat span and no execute_tool spans at all. The 17-inference read loop is the same story in reverse: a wall of near-identical read_page calls that you see at a glance and would never notice from the answer.

A related one, a search spiral of twelve search_docs calls with the last four textually identical, was also a trace finding rather than a code-reading finding.

Invariants 1 and 2 came from elsewhere — Instruments’ Foundation Models template showed me an inference labelled VERIFY while it was still calling read_page, which is what exposed the phase machine disagreeing with the prompt.

Turn 1 looks flawless and turn 2 looks like the model got lazy. That class of bug survives a demo comfortably. It is the clearest argument I have for instrumenting before you think you need to.

Verification returns evidence, not a verdict

check_claim could return supported: true/false. It doesn’t. It returns the source text and asks the model to compare.

A boolean would just be the model’s own opinion laundered through a tool call — it’d feel like verification while adding nothing. Returning the evidence forces a comparison against something the model can actually see.

Running code to verify code

The brief I set myself said the agent should be able to search, read a page, run a code snippet, or respond. That third one is easy to read as “the agent can do arithmetic,” which produces a calculator tool that never once fires on a documentation corpus.

Read it differently — “the agent can check the code it’s about to hand you” — and it becomes the most useful verification path in the app.

I measured before building anything:

chunks in the corpus1081
containing a fenced code block497 (46%)
containing Python327 (30%)

Roughly a third of everything this agent retrieves is code it has never run. That’s the largest unverified surface in the app.

So run_snippet sits in the verify phase next to check_claim. Prose gets verified by re-reading its source; code can’t be — a snippet can be quoted from the docs word-perfect and still fail against the installed package, because a symbol got renamed. Execution is the only check that catches that.

prose claim  →  check_claim   →  re-read the source
code claim   →  run_snippet   →  execute it

The sandbox

(version 1)
(allow default)
(deny network*)
(deny file-write*)
(allow file-write* (subpath "<resolved scratch dir>"))

Plus an empty environment, HOME inside a throwaway directory, and a 20-second cap.

This is accident containment, not a security boundary, and the code says so in three places. The profile starts from allow default and subtracts, which is a denylist, and denylists don’t hold against someone trying to get out. It reliably stops code copied out of documentation from phoning home. It would not stop hostile code.

Reporting failure honestly

Failure comes back as information, and the kind of failure is classified — because “this code is broken” and “I couldn’t run it here” are opposite conclusions and the model will act on whichever one it’s told:

OutcomeWhat the model is told
ran cleanpresent the code, quote the output
blocked at networkimports resolved, names exist — present the code as correct
no valid credentialsa 401 says nothing about the code — same
timed outtreat as unverified
anything elsea bad import means the docs or the snippet is wrong — say so

Without those middle two, the agent reads an environment failure as a documentation defect and tells the user their example is broken. That’s worse than not running it at all.

Tracing: Weave’s agent model over raw OpenTelemetry

Now the part this whole project exists for.

Weave’s agent tracing data model is three span types: invoke_agent for a turn, chat for a model inference, execute_tool for a tool call, all grouped by a conversation id. In Python you get this from the SDK. From Swift you get to build it.

A single turn in Weave's Agents view. 18 spans, emitted from Swift.

That screenshot took considerably longer to earn than it looks. Here’s what I hit.

Finding 1: there are two endpoints, and the wrong one returns 200

Weave’s OTel documentation lands you on:

https://trace.wandb.ai/otel/v1/traces

That endpoint feeds the Traces and Threads views. It does not populate the Agents view — it doesn’t produce the agent data model at all. The correct endpoint is on a different page:

https://trace.wandb.ai/agents/otel/v1/traces

The wrong one accepts your spans, returns HTTP 200, and shows them in a view. Everything looks like it worked. You only discover the problem when you open the Agents tab and it’s empty — and at that point the natural assumption is that your attributes are wrong, not your URL.

For anyone on the SDK-free path this is the single highest-risk step in the integration, and it has the least signposting.

Finding 2: one attribute key can silently delete an entire span

This is the worst one, and it affects the official Python SDK too.

If a span carries an attribute key that is a dotted prefix of another key on the same span — say gen_ai.usage.input_tokens and gen_ai.usage.input_tokens.cached — Weave discards the whole span. Silently. On a 200.

Seven out of seven reproducible. The parent span still renders, so nothing looks missing; you just have a turn where one model call quietly doesn’t exist.

I now guard against it at emit time:

// A key that is a dotted prefix of another key on the same span makes the
// backend drop the entire span, silently, on a 200. Trap it in debug.
WeaveAttributeGuard.assertNoCollisions(attributes)

Finding 3: custom attributes are stored and never rendered

I put my retrieval diagnostics — BM25 scores, dense scores, what RRF dropped — into custom span attributes. They vanished. Not rejected, not errored: accepted, stored, and never displayed anywhere in the UI.

The workaround turns out to be nicer than the original plan. Put the diagnostics inside gen_ai.tool.call.result as JSON, and Weave renders them as an inspectable field table:

Retrieval diagnostics rendered as an inspectable field table by shipping them inside the tool result instead of as custom attributes.

Two things Foundation Models forces you to handle

Span parents can’t ride on @TaskLocal. This is the elegant solution — Swift’s task-local storage is exactly OTel context propagation, and it’s what my tracing library offers. It does not survive Foundation Models. The framework dispatches tool and lifecycle callbacks from its own machinery, and nothing guarantees they run on the task that opened the turn — or that they run one at a time. Parents get passed explicitly.

.onResponse fires once per turn, not per inference — on-device. Over chat-completions it fires mid-turn, which I discovered by shipping a “fix” that withdrew tools in the middle of research. An inference ends in either a tool call or the final response, so .onToolCall and .onResponse both close the chat span, guarded by a pending flag.

Checking what you sent before blaming the renderer

For a while my chat spans had output that read (Response) The user is asking…. I had written "\(response)" where response was a Swift type with a CustomStringConvertible conformance, so Weave was faithfully rendering a type dump as the conversation preview. response.text fixed it.

The general point is worth stating: an empty field or a mess in someone else’s UI is not evidence about their code until you have checked what you actually sent. I had to relearn that more than once — later on, two template variables came back empty in Signals for exactly the same reason.

Signals: what an error rate cannot see

With traces flowing, the next question is is it going wrong right now? That’s Weave Signals: LLM scorers that run automatically over production traces as they arrive.

Here is the motivation, from this project’s own traces. Across development I accumulated 1,033 spans and 14 errors — a 1.4% error rate.

That number is misleading.

Almost every failure that mattered was a confident wrong answer, which a trace records as a success. One conversation returned “the documentation does not explicitly mention a Python SDK” across 72 spans with zero errors. Wrong, and invisible to every metric I had.

A span-level error rate is structurally incapable of seeing the characteristic failure of a documentation agent. An LLM reading the output can see it. That’s the case for Signals in two sentences.

Designing the scorers

I set up two. One is the stock Low Quality Response preset, unmodified — partly to check the built-ins work on OTel-ingested traces, and partly as a second opinion. That second job turned out to matter.

The other is custom, and its design was forced by something I found in the product: the documented “Ratings” category doesn’t exist in the shipped UI. Only Tags. And a tag that matches nothing renders no row at all — so a non-exhaustive tag set produces a table where absence is ambiguous.

The fix is to make the tag set mutually exclusive and exhaustive, so exactly one always fires:

TagFires when
well-groundedevery substantive claim is attributed to a cited page
partially-groundedsome claims cited, core facts asserted bare
ungroundedconfident claims, no attribution at all
unsupported-absencethe answer’s substance is a denial

That last tag is the one worth explaining. This agent’s characteristic failure is the well-cited denial — an answer that cites two real pages and then wrongly concludes the docs don’t cover something. Without giving denials their own bucket, those score as well-grounded: the citations are genuine, only the conclusion is false. A denial is only as strong as the search behind it, and the scorer can’t see the search. So denials go to human review rather than being judged.

Online scoring over OTel-ingested turns.

What it found

Zero substantive answers scored well-grounded. Every good answer came back partially grounded, with reasons like:

“Only the claim about the trace guide is cited; use of @weave.op and weave.init are stated without source attribution.”

That’s a real, specific, actionable defect. My agent is instructed to cite the page and url for every substantive claim, and it cites the framing while asserting the actual API facts bare. Nothing else caught it — the spans are clean, the answers are correct, the error rate is 0.5%.

The whole scoring run cost seven hundredths of a cent.

Evaluation: a dataset designed to fail

Signals tells you something is wrong. It can’t tell you how wrong, on what kind of question, or whether your fix helped. For that you need a fixed dataset and weave.Evaluation.

weave.Evaluation is Python and the agent is Swift, so the two have to meet somewhere — and where they meet determines what the numbers actually describe.

The bridge

I gave the app a loopback HTTP endpoint and drove the running app from Python.

flowchart LR
    NB["notebook<br/>weave.Evaluation"] -->|"POST /ask"| APP["AskWeave.app<br/>Settings ▸ Evaluation ▸ Start"]
    APP -->|"agent traces<br/>raw OTel"| P["askweave-evals"]
    NB -->|"eval rows + scores<br/>Weave Python SDK"| P

The endpoint serves the same session, the same phase machine, the same bundled index and the same tracer that the UI drives. What gets measured is the application, not a reimplementation of it — and because the server is long-lived, model load is paid once rather than on every row.

Note what’s happening in that diagram: two independent write paths into one Weave project. Agent behaviour arrives as raw OTel from Swift; the evaluation arrives through the Python SDK. They’re joined by the conversation_id the endpoint returns, so every scored row links back to the trace that produced it.

The endpoint is started from a panel inside Settings, and while it’s running the settings sheet locks — the model picker is disabled and the sheet won’t dismiss. That’s deliberate: every eval row builds a fresh agent from current settings, so changing the model halfway splits your baseline across two models and reports one average describing neither. Making it impossible beats documenting it.

The eval endpoint, running. The Model tab is disabled — you can't change the model under a running evaluation.

The dataset

Twelve questions. The design principle: a question is only worth including if a plausible-looking answer can be wrong. Questions that are easy to answer well tell you nothing.

KindRowsWhat it tests
factual4ordinary lookups, including two-part answers
multi-hop2genuinely needs two pages
multi-hop-trap1correct answer needs a caveat that’s easy to omit
hallucination-bait2the question presupposes something false
ambiguous2scored on whether the ambiguity is handled
multi-turn1only answerable with the previous turn in context

Two examples:

sampling-ten-percent — “My trace volume is getting expensive. How do I keep only 10% of traces?” The correct answer names both mechanisms and says server-side ingest sampling is self-managed only. Recommending it to a SaaS user is confidently wrong and looks completely actionable.

bleu-scorer — “How do I use Weave’s built-in BLEU scorer?” There isn’t one. The built-ins stop at EmbeddingSimilarityScorer, which is exactly the tempting substitute — so the row catches both fabrication and silent substitution of a near neighbour.

Every row carries reference notes as well as a reference answer — what to accept, what to reject, and the specific failure it targets. Without notes, a judge grades paraphrase similarity to your reference, which is not the same thing as grading correctness.

The scorers

Four: three deterministic, one LLM judge. The mix is the point.

@weave.op
def citation_validity(expected_sources: list[str], output: dict) -> dict:
    """Do the cited URLs exist, and did any expected page get cited?"""
    cited = output.get("cited_urls", [])
    invalid = [u for u in cited if u not in CITEABLE]
    return {
        "cited_count": len(cited),
        "invalid_count": len(invalid),
        "all_valid": len(cited) > 0 and not invalid,
        "hit_expected_source": bool(expected & set(cited)),
    }

CITEABLE is built from the actual pinned corpus — not a regex for “looks like a link”. A fabricated but plausible URL is the most convincing kind of hallucination, and this catches it with certainty and no model in the loop.

agent_behaviour reads the tool calls and checks the loop actually did its job. It earns its place for a specific reason: Weave Signals can’t see tool calls at all, and the LLM judge only sees text. It’s the only scorer in the whole setup that can distinguish a grounded answer from a fluent one recalled from the model’s own parameters — which look identical from outside.

The judge scores groundedness, completeness, premise handling and hedging, plus an overall that is explicitly not a mean — one fabricated fact should sink a row regardless of how it scores elsewhere. It runs on W&B Serverless Inference (DeepSeek-V4-Pro), which is a different provider from the agent, resolved against /v1/models at startup, with the harness refusing to run if judge and agent match.

Results

12 rows × 2 trials, on Claude Haiku. Overall 0.64. Zero failures, and 100% of turns searched, read a page, and verified — the loop never skipped a step across 24 runs.

But the average is nearly useless. The spread is the result:

Three findings:

Ambiguity is the weakness. Both ambiguous rows scored 0.30 on premise handling, reproducibly. Asked “How do I get started?”, the agent silently picks tracing and presents it as the only path. It also burned 15.5 tool calls and 24 seconds on that question — the most expensive row in the set. An ambiguous question makes this agent search harder instead of asking.

Groundedness was weakest at 0.56 — and this is the same defect Signals reported independently, on different data, with a different scorer and a different judge model. Two instruments, one conclusion. That convergence is worth more than either result alone.

swift-sdk scored 0.40 while being correct. It correctly denied the Swift SDK, cited nothing at all, and suggested running the TypeScript SDK under Node rather than the OpenTelemetry path this entire application is built on.

When your instruments disagree

This is the part I did not see coming, and the reason I would have written this post even if nothing else had worked.

Two of my “failures” were bugs in the evaluation

redact-pii. My citation scorer flagged an invalid URL: microsoft.github.io/presidio/supported_entities. That URL is linked from the Weave documentation itself — Weave’s PII redaction is built on Presidio and the entity list lives upstream. My scorer only accepted URLs inside the corpus, so a perfectly good citation read as a fabrication.

Worse: the agent’s answer described installing the Presidio packages, which the docs require and my reference answer had left out entirely. The agent was marked down for being more correct than the reference it was graded against.

trace-a-function. Missed hit_expected_source because it cited create-call rather than ops. But create-call.md contains more @weave.op material than ops.md does. The citation was good; my expectation was wrong.

In both cases the deterministic scorer was wrong and the LLM judge was right. Which neatly inverts the reason I’d given for having deterministic scorers in the first place — I’d written that they “cannot be talked into anything.”

True, and beside the point. A deterministic scorer can’t be argued out of its assumption. It also can’t notice the assumption is wrong. Determinism buys consistency, not correctness — and a confidently wrong deterministic scorer is harder to catch than a wobbly judge, because it never looks uncertain.

The Signals scorers caught each other

Same story, different pillar. A truncated, errored turn scored well-grounded — my best rating — because my rubric said “a refusal that makes no factual claims counts as well-grounded”, and a turn that produced nothing technically makes no claims. The stock Low Quality Response preset, looking at the identical turn, correctly called it low quality.

A single LLM judge is an opinion with a number attached. A second one cost nothing extra and found a bug in my rubric on turn 2 of 8.

I fixed two things, and one of them worked

I made two changes to the agent and re-ran. 0.640 → 0.658. Not much. But which half moved is the whole story:

FixResult
Citation discipline✅ worked — all_valid 1.000, nothing uncited, groundedness +0.046
Ambiguity handling❌ failed — premise handling flat

The ambiguity answers came back near-verbatim identical to the baseline. I’d added the instruction and the behaviour didn’t move at all.

Here’s why, and it’s a design lesson rather than a prompt-tuning one. I put the fix in the answer phase. By the time the answer phase runs, research and verify have already committed to one reading — it searched for tracing, retrieved tracing pages, verified tracing claims. The answer phase is handed one-sided evidence and simultaneously told “answer only from what the retrieved pages actually said.”

Asking it, at that moment, to name the readings it never researched is asking it to contradict the grounding rule. Given the conflict, it obeys the older, stronger instruction.

Ambiguity is a research-phase decision, not an answer-phase one. It has to be detected before retrieval commits to an interpretation, because afterwards the evidence itself is one-sided.

Which is the same shape as the onPrompt bug from earlier: a correct instruction placed at the wrong point in the loop.

And Weave caught my methodology error

I’d changed both the instrument and the agent in the same step — sloppy, and I knew it. When I opened the comparison, Weave had flagged “Dataset inconsistency detected” and “Scoring inconsistency detected”, and quietly excluded from the row-level diff exactly the two rows whose definitions I’d changed.

Weave noticing that my A/B wasn't a clean A/B. Object versioning earning its keep.

I didn’t tell it any of that. It worked it out from the object versions. Later, when I edited a Signals scorer, it did the same thing — versioned the scorer and badged the existing rows v0, so old scores stay attributed to the rubric that produced them instead of being silently reinterpreted under the new one.

Twice, Weave’s versioning protected a result from me. That is a better argument for versioned datasets and scorers than any feature page.

The synthesis

Three instruments, and each caught something the others structurally could not:

CatchesCannot see
Tracingstructure — which tools ran, in what order, with what payloadwhether the answer was any good
Signalsquality on live traffic, including questions you never thought to asktool calls; and it has no ground truth to compare against
Evaluationquality against known answers, per failure mode, reproduciblyanything outside the twelve rows you wrote

Tracing proved the loop runs — and gave the agent_behaviour scorer the tool-call data it scores on. Signals found the citation gap first, on real usage, with no dataset at all. Evaluation quantified it, localised it by question type, and gave me a baseline to measure a fix against.

Signals said something is wrong here. Evaluation said how wrong, on what, and compared to what. Neither substitutes for the other.

Closing thoughts

Two things I am taking away from this.

The first is about instruments. I went in thinking observability was something you add to a project to find out whether it works. What actually happened is that the observability layer found bugs in itself twice, found a defect in the agent that no test would have caught, and — through Weave’s object versioning — caught a methodological error in how I was running my own experiment. The instruments turned out to be as much a subject of the investigation as the agent was.

The second is about the SDK-free path. It works. Everything in Weave’s agent data model is reachable from Swift with hand-built protobuf, Signals score those traces, and evaluation rows link back to them. It took twelve findings’ worth of discovery to get there, and almost all of that was signposting rather than capability.

Thanks for reading.
