Product recommender: Foundation Models and a server-hosted vector database to recommend from 1.6 million products

Building a product recommender using a hybrid RAG approach, performing semantic search on a server-side vector database and generating recommendations on-device with the Foundation Models framework.
Sunday, August 16, 2026

On-device Foundation Models are a great fit for tasks like summarization, grammar correction, entity extraction, tagging, and sentiment analysis. For those workloads, the data usually has one of two convenient properties:

  1. It fits into the model’s context window.
  2. It fits on the device.



1.6 million products!



What if the data you want to provide to the LLM is so large that it won’t fit on the device?
A popular approach for large datasets is Retrieval Augmented Generation (RAG): retrieve only the relevant records, fit those records into the model’s context window, and then ask the model to answer or reason over that smaller context.

That works beautifully when the retrieval index itself can live on device. Product catalogs, support archives, documentation corpora, and enterprise knowledge bases are often too large for that. In those cases, retrieval needs to happen on a server, while generation can still happen privately on device.

When you have millions of products😱:
Consider online retailers like Amazon or Best Buy with millions or billions of documents and catalog data, that won’t fit on device. To answer a user’s product-related question, you must first retrieve the relevant product details by running a semantic search on the entire catalog, and then provide it to the LLM to reason about and answer the user’s question. This clearly can’t be done on-device!

This is exactly the problem we’ll tackle in this article. The solution requires a hybrid on-device and server-side approach. The dataset lives in a cloud or on-prem server and is retrieved on demand based on the user’s query. The retrieved documents are then processed with on-device Foundation Models to deliver intelligent responses.

To illustrate this approach, we’ll build a Product recommender app, which will search through 1.6 million Amazon products and generate a recommendation using the on-device Foundation Models.



The App: A Product recommender that recommends from 1.6 million products

We’ll build a proof-of-concept product discovery app 🛍️ that uses on-device Foundation Models to generate recommendations from a server-hosted product database using Retrieval Augmented Generation (RAG).

Product Recommender Key Features 🌟

  • Recommends products from over 1.6 million electronics based on your natural language query.
  • Performs semantic search against a Qdrant vector database running in a container using  Apple container
  • Uses an on-device Core ML model (all-MiniLM-L6-v2) to generate vector embeddings for your queries securely on your device. 🤖
  • Leverages the Foundation Models framework API with @Generable to generate structured summaries and product lists.
  • Communicates with the Qdrant database using a type-safe client built at compile time with the  Swift OpenAPI Generator.

Overall architecture

This is the complete, hybrid architecture of the Product Recommender app, which combines on-device Foundation Model with a server-side vector database for semantic search on 1.6 million products.

  • 1. User Query: The user types a natural language query, like “Projector screen for outdoors,” into the ProductSearchView.
  • 2. Embed user query: The app uses the on-device all-MiniLM-L6-v2.mlpackage Core ML model to convert the user’s text query into a vector embedding.
  • 3. API Request: The app’s QdrantClient takes this vector and builds a search query. This client code was auto-generated from Qdrant’s OpenAPI spec using Swift OpenAPI Generator, which gives the app a type-safe HTTP client.
  • 4. Server-Side Search: The HTTP request is sent to the Qdrant database microservice. For local testing, the database runs on a Mac using Apple container. In production, the same service could run in a cloud-hosted container environment. Qdrant then performs a high-speed vector search against its database of 1.6 million products.
  • 5. Product Results: Qdrant identifies the top matching products and returns their associated metadata in the payload (like title, ASIN, ratings, and image URLs) back to the app running on iOS.
  • 6. On-Device Reasoning: The app receives these raw product results. It then passes this context (the user’s original query + the retrieved product data) to the on-device Foundation Models.
  • 7. Structured Generation: The Foundation Model uses @Generable structs (ProductRecommendations) to generate a summary and a structured list of recommendations based only on the retrieved context.
  • 8. Display Results: This structured response is streamed to the UI, and because the database payload included the Amazon ASIN (parent_asin), the user can tap a product, and the app opens the Amazon web page for that item.

Preparing the Qdrant vector database

First we’ll set up the backend for the product recommender app. This involves launching a Qdrant vector database, downloading the Amazon product dataset, and then embedding and storing the product records in Qdrant.

Qdrant is one of many popular vector database options available to store text embeddings for semantic search. Vector databases are designed for storing embeddings and performing fast similarity search, making it ideal RAG applications.

In this section we’ll set up the Qdrant database on the Mac, but rather than install it natively, we’ll run it in a container using the newly announced Apple container. Apple container lets you launch and run Linux containers on the Mac, which you can later easily push to the cloud for server-side hosting.

Apple container: https://github.com/apple/container

Launching Qdrant with Apple Container

After you’ve finished installing Apple container on your Mac, we can get our vector database up and running easily:

This shell command handles the initial Qdrant setup:

container run -it --rm \
	--volume "$(PWD)/qdrant_storage:/qdrant/storage" \
    --name qdrant \
    qdrant/qdrant

This command does a few key things which should all be super familiar to you if you are a Docker user:

  • container run -it --rm: This tells the container CLI to run a new container in interactive mode (-it) and to remove the container once it’s stopped (--rm).
  • --volume "$(PWD)/qdrant_storage:/qdrant/storage": Here we mount our storage into the container for data persistence. It maps a directory named qdrant_storage in your current working directory to the /qdrant/storage directory inside the container. Even if the container is stopped and removed, your vector database data will remain safe on your Mac.
  • --name qdrant: We give our container a memorable name, qdrant.
  • qdrant/qdrant: This is the official Qdrant image from the Docker Hub.

Qdrant networking with Apple container

Once the Qdrant container is running, we need a way for our Mac to communicate with it. This was my first struggle using Apple container coming from Docker on Linux. In a prior life I worked exclusively on containerized AI workloads on AWS, particularly containers that run accelerated workloads. During local testing with Docker on a Linux box you would simply do --network=host and this would expose container services to the OS. Apple container’s networking is a bit more complicated as described in the doc under limitations.

Thankfully, there is a straightforward workaround: route traffic manually using socat. The helper script below forwards Qdrant’s API ports from the container IP to your Mac. Run it in a separate terminal window and keep it open while testing.

#!/bin/bash

ip=$(container inspect qdrant | jq -r '.[0].networks[0].address' | cut -d'/' -f1)

# Start socat for each port and record PIDs
pids=()

for port in 6333 6334; do
  echo "Forwarding localhost:$port -> $ip:$port"
  # socat TCP-LISTEN:$port,fork,bind=127.0.0.1 TCP:$ip:$port &
  socat TCP-LISTEN:$port,fork,reuseaddr,bind=0.0.0.0 TCP:$ip:$port &

  pids+=($!)
done
...

Here’s the breakdown of the script:

  1. It first inspects the running qdrant container to get its internal IP address.
  2. Then, it uses socat to forward ports 6333 (for the gRPC API) and 6334 (for the REST API) from your localhost to the corresponding ports on the container’s IP address. This allows you to interact with the Qdrant database as if it were running directly on your Mac.

Embedding and Upserting Data into Qdrant

With the data downloaded, the next step is to convert the product information into vector embeddings and “upsert” them into our Qdrant database. “Upsert” is a combination of “update” and “insert” – if a product with the same ID already exists, it will be updated; otherwise, it will be inserted.

We use the sentence-transformers/all-MiniLM-L6-v2 model to generate the embeddings. For each product, we create a combined text string of its title, features, and description. This text is then fed into the model to produce a vector embedding.

from qdrant_client.http.models import PointStruct
from sentence_transformers import SentenceTransformer

model = SentenceTransformer('all-MiniLM-L6-v2', device='mps')

Query Qdrant to retrieve products

Now for the real test. We will write a function that takes a plain text query, embeds it using the same all-MiniLM-L6-v2 model, and then sends that vector to Qdrant to find the most semantically similar products.

from qdrant_client import QdrantClient
from sentence_transformers import SentenceTransformer
from pprint import pprint

model = SentenceTransformer('all-MiniLM-L6-v2', device='mps')
client = QdrantClient(host="<YOUR_IP>", port=6333, timeout=60.)

def search_qdrant(query: str, collection_name: str, search_limit: int = 3):
    """
    Performs a vector search on a specified Qdrant collection using the modern API.
    """
    vector = model.encode(query).tolist()
    
    query_result = client.query_points(
        collection_name=collection_name,
        query=vector,
        limit=search_limit,
    )
    print("======================")
    print("printing query_result")
    pprint(query_result.points[0].payload)
    print("======================")
    
    return query_result.points

This search_qdrant function does the full end-to-end process:

  1. Initializes the QdrantClient, this time connecting to localhost through the socat port forwarding script.
  2. The function search_qdrant encodes our text query into a vector.
  3. It then uses client.query_points() to find the top 3 (limit=3) vectors in our collection that are closest to our query vector.
  4. Finally, it prints the payload (the product metadata) of the single best match.

Convert Embedding Model to Core ML Format

Next, we’ll get the embedding model, all-MiniLM-L6-v2, ready for the iOS app. This involves converting the model from its original format into Apple’s Core ML format, which is optimized for on-device performance.

Downloading the model from Hugging Face

First, we need to download the model and its tokenizer from the Hugging Face Hub

from transformers import AutoTokenizer, AutoModel

hf_model_id = "sentence-transformers/all-MiniLM-L6-v2"

hf_model = AutoModel.from_pretrained(hf_model_id)
hf_model.save_pretrained(model_path)

tokenizer = AutoTokenizer.from_pretrained(hf_model_id)
tokenizer.save_pretrained(tokenizer_path)

Wrapping and Tracing the Model

The raw output of the all-MiniLM-L6-v2 model is not quite what we want the model to return. We want our model to perform mean pooling on the token embeddings and then normalize the result to get the final sentence embedding. To handle this, we’ll create a PyTorch wrapper class and convert the wrapper model to CoreML:

import torch

class TracingWrapper(torch.nn.Module):
    def __init__(self, model):
        super().__init__()
        self.model = model

    def forward(self, input_ids, attention_mask):
        outputs = self.model(input_ids=input_ids, attention_mask=attention_mask)
        token_embeddings = outputs.last_hidden_state  # [batch, seq_len, hidden]

        # Expand attention_mask to [batch, seq_len, hidden]
        mask = attention_mask.unsqueeze(-1).expand(token_embeddings.size()).float()

        # Sum the embeddings and divide by the number of valid tokens to get mean
        sum_embeddings = torch.sum(token_embeddings * mask, dim=1)
        sum_mask = torch.clamp(mask.sum(dim=1), min=1e-9)  # prevent division by zero
        pooled = sum_embeddings / sum_mask  # [batch, hidden]

        # Normalize the pooled vector
        norm = torch.linalg.norm(pooled, dim=-1, keepdim=True)
        normalized_pooled = pooled / (norm + 1e-12)

        return normalized_pooled

With the wrapper in place, we can now “trace” the model. Tracing records the operations performed on a sample input, creating a static computational graph that Core ML can understand.

# Wrap the model
wrapper = TracingWrapper(hf_model)

with torch.no_grad():
    wrapper.eval()
    prompt = "isn't it nice to be inside such a fancy computer"
    tokenized_prompt = tokenizer(prompt, return_tensors='pt')

    example_input = tokenized_prompt['input_ids']
    example_attention_mask = tokenized_prompt['attention_mask']

    # Now trace the wrapper
    traced_model = torch.jit.trace(wrapper, (example_input, example_attention_mask))

Converting to Core ML

We can now convert our traced model to the .mlpackage format using coremltools. We’ll specify the expected input shapes and data types, and we’ll also take advantage of 16-bit float (FP16) precision to reduce the model’s size and improve performance.

import coremltools as ct
import numpy as np

input_size = ct.RangeDim(lower_bound=1, upper_bound=511, default=1)
batch_size = ct.RangeDim(lower_bound=1, upper_bound=64, default=1)

inputs = [ct.TensorType(shape=(batch_size, input_size), dtype=np.int32, name="input_ids"),
          ct.TensorType(shape=(batch_size, input_size), dtype=np.int32, name="attention_mask")]
outputs = [ct.TensorType(dtype=np.float32, name="embeddings")]

coreml_model_fp16: ct.models.MLModel = ct.convert(
        traced_model,
        inputs=inputs,
        outputs=outputs,
        compute_precision=ct.precision.FLOAT16,
        compute_units=ct.ComputeUnit.CPU_AND_GPU,
    )

Finally, we save our Core ML model:

save_path = os.path.join(model_dir_path, f"{model_name}-fp16.mlpackage")
coreml_model_fp16.save(save_path)
print(f"Model saved at: {save_path}")

Accessing Qdrant with Swift OpenAPI Generator

While Qdrant provides a convenient Python client, no official client exists for Swift. We can address this by using Qdrant’s OpenAPI specification and Swift OpenAPI Generator to create a type-safe Swift client.

The Python verification step used Qdrant’s query_points API. Here is what that call looks like with the Python client.

Qdrant Python Client

Qdrant provides the qdrant-client package, in which the query_points API can be called like this:

from qdrant_client import QdrantClient
from sentence_transformers import SentenceTransformer

client = QdrantClient(host="localhost", port=6333)

Qdrant OpenAPI spec (openapi.json)

Now let’s take a look at the OpenAPI spec for the query_points API provided by Qdrant. You can download the openapi.json file from Qdrant’s GitHub repository.

Qdrant OpenAPI Spec: https://github.com/qdrant/qdrant/blob/master/docs/redoc/master/openapi.json

This file includes definitions for all Qdrant APIs. The query_points endpoint is defined as a POST operation.

{
  "paths": {
    "/collections/{collection_name}/points/query": {
      "post": {
        "tags": [ "Search" ],
        "summary": "Query points",
        "description": "Universally query points...",
        "operationId": "query_points",
        "parameters": [
          {
            "name": "collection_name",
            "in": "path",
            "required": true,
            "schema": { "type": "string" }
          }
        ],
        "requestBody": {
          "description": "Describes the query to make to the collection",
          "content": {
            "application/json": {
              "schema": {
                "$ref": "#/components/schemas/QueryRequest"
              }
            }
          }
        },
        "responses": {
          "200": {
            "description": "successful operation",
            "content": {
              "application/json": {
                "schema": {
                  "type": "object",
                  "properties": {
                    "result": {
                      "$ref": "#/components/schemas/QueryResponse"
                    },
                    /* ... */
                  }
                }
              }
            }
          }
        }
      }
    }
  }
}

You’ll notice that the Python’s client.query_points(...) function directly corresponds to the query_points operationId from the JSON. The Python client handles all the underlying HTTP requests and JSON serialization, allowing you to pass simple arguments like collection_name and query.

The JSON defines the endpoint with Path, Operation ID, Request Body and Success Response.

Generating the Swift API from openapi.json

Swift OpenAPI Generator: https://github.com/apple/swift-openapi-generator

Since no official Swift client exists, we can use Swift OpenAPI Generator to generate the client code. We can add this as a build plugin to our project, pointing it at the openapi.json file. The Swift OpenAPI Generator can read any OpenAPI specification file and automatically generate a type-safe, efficient, and correct Swift client.

At build time, the generator creates Client.swift and Types.swift in the project’s derived data. These files are generated artifacts and should not be edited directly. They can be found here:

/Users/USER_NAME/Library/Developer/Xcode/DerivedData/YOUR_PROJECT-xxxxxxxx/Build/Intermediates.noindex/BuildToolPluginIntermediates/.../GeneratedSources/

For example, this is what the generated query_points API in Client.swift looks like:

Generated Client.swift:

// This code is auto-generated by swift-openapi-generator

internal protocol APIProtocol: Sendable {
    
    // ... all other Qdrant APIs are also generated here ...

    /// Query points
    ///
    /// Universally query points. This endpoint covers all capabilities...
    ///
    /// - Remark: HTTP `POST /collections/{collection_name}/points/query`.
    /// - Remark: Generated from `#/paths//collections/{collection_name}/points/query/post(query_points)`.
    func query_points(_ input: Operations.query_points.Input) async throws -> Operations.query_points.Output
}

You can see that the generator has created a Swift protocol with a function query_points. This function takes a single Input object and returns a complex Output object and these types are all defined in the accompanying Types.swift file.

Creating a Swift Client Wrapper

Using the generated client interface, we can generate a friendly Swift QdrantClient struct to interface with our Qdrant database.

QdrantClient.swift:

import Foundation
import OpenAPIRuntime
import OpenAPIURLSession

struct QdrantClient {
    
    private let client: Client
    
    init(hostname: String, port: String) throws {
        ...
        self.client = Client(serverURL: serverURL, transport: URLSessionTransport())
    }
    
    func search(vector: [Float], collectionName: String, limit: Int) async throws -> [Product] {
                
        let withPayload = Components.Schemas.WithPayloadInterface(value1: true)
        let vectorInput = Components.Schemas.VectorInput(value1: vector)
        let queryInterface = Components.Schemas.QueryInterface(value1: vectorInput)
        let queryPayload = Components.Schemas.QueryRequest.queryPayload(value1: queryInterface)

        let queryRequest = Components.Schemas.QueryRequest(
            query: queryPayload,
            limit: limit,
            with_payload: .init(value1: withPayload)
        )
        
        let body = Operations.query_points.Input.Body.json(queryRequest)
        
        let response = try await client.query_points(
            path: .init(collection_name: collectionName),
            body: body
        )
        
        ...
        // Parsing code to load returned response into [Product] array data model.
        ...
    }
}

How it all comes together

Let’s trace the flow of a user query through the app:

  1. User Input: The user types a query into the text field in ProductSearchView.swift.

  2. Embedding Generation: In RecommendationViewModel.swift, the findRecommendations() method calls our EmbeddingGenerator to convert the user’s query into a vector embedding using the on-device Core ML model.

  3. Qdrant Search: The view model then uses the QdrantClient to send this embedding to our Qdrant database and retrieve a list of similar products. On the server side, you can monitor requests from the database log.

  4. Foundation Models for recommendations: The retrieved product data is then formatted into a prompt and sent to the Foundation Models API.

    let summaryStream = session.streamResponse(
    generating: ProductRecommendations.self,
    options: .init(sampling: .greedy)
) {
    "User Query: \(userQuery)"
    "Products:\n"

        "### Product \(index + 1) ###\n"
        "Title: \(product.title ?? "N/A")\n"
        "ASIN: \(product.parentAsin)\n"
        ...
    }
    "\nPlease provide a recommendation based on the user's query and the provided products."
}

  5. Displaying the Results: The streamed response from the Foundation Models API is displayed in real-time in our ResultView, which uses ProductCardView to create a rich and interactive UI for each recommended product.

And with that, our product recommender is complete. In this article, we’ve built a hybrid solution that directly tackles the challenge we started with: how to leverage the on-device Foundation Models when your data is far too large to fit on the device. Using a hybrid RAG architecture we saw how to keep the semantic search “heavy lifting” on the server, using Qdrant in a container to search through millions of products for the most relevant items. On the device the app receives just a topk relevant products, which the Foundation Model uses to generate a recommendation to the user.
